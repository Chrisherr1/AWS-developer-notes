**CloudWatch Basics**
---
    CloudWatch is a core supporting service within AWS which provides metric,log and event management services.

    It's used through other AWS services for health and performance, monitoring, log management, and serverless architectures.

At the high level CloudWatch is a service that collects and manages operational data on your behalf.

Vocab: Operational Data - is data generated by an environment either detailing how it performs, how it nominally runs, or any logging data it generates.

CloudWatch is 3 MAIN Products:
    1. CloudWatch itself - Metrics: AWS Products,Apps, on-Premises
        - Resource utilization,number of requests,etc.
        - Can be used to monitor either inside AWS or even other cloud platforms.
        *BONUS* Some Applications gather data natively LMAO, Meaning anything shown by the product in AWS can be handled natively.

    2. CloudWatch Logs - AWS Products,Apps, on-Premises
        - Allows for the collection, monitoring, and actions based on logging data.
        - This is only for the services, themselves, for monitoring stuff inside the instances for example you'd need to install the CloudWatch Agent on the system to get that monitoring.

    3. CloudWatch Events - AWS Services & Schedules
        - Allows AWS service to automatically do something when an event occurs.. For example if a instance shutdown for some reason it counts as an event to start another one eg.

        - or have it so that something happens at a specific time of day or schedule something to happen.

        - A budget alarm is an example of a event causing something to happen -> send a notification to my phone.

        - May be used for upscaling, or downscaling.


**Basic Architecture**
    - AWS services give data to cloud watch -> Cloud watch can then give statistics based on that data && Activate any EVENTs that correlate to what's happening based on the data (autoscaling or alerts)


**Namespace**
---
    It acts as a container for monitoring data.

    It acts as a way to keep things from getting messy and to be able to separate things into different areas.

    They can be called anything as long as it follows the rules.

**NOTE**
    All AWS data goes into an AWS namespace.

    Convention is usually something like AWS/'service'

    EG: AWS/EC2 - which is the namespace used for all ec2 data.

    YOU CANNOT USE THIS NAMING CONVENTION, it's reserved for AWS.

    You can create a namespace, and store data just can't copy the naming convention of AWS.

    BUT usually namespaces contains related metrics.

**what is a metric?**

    A metric is a collection of related data points in a time ordered structure.

    eg: CPU utilization,network in/out,disk util
        They're all metrics.
    
    A metric is not for a specific server, it's more for whole service as a whole.


**what is a datapoint?**

    A datapoint consists of 2 things:
        1. Time Stamp - Includes time basically.(TimeZone)
        2. Value - represents the actual data we're are being given so in this instance it would be CPU utilization.


*How do we separate metrics?*

    We can separate metrics using `Dimensions`.

    This can be useful if you don't want the aggregated information and only want the metric of a specific instance for example.

**Dimensions are separate datapoints for different things or perspectives within the same metric.**


Usually the service before aggregation gives the instance ID of the service so it can be referenced more easily.


**CloudWatch also allows us to set up automatic actions based on metrics and this is done using *Alarms***

An Alarm is linked to a specific metric, then based on configuration will do an action based on that metric.

Alarms have 2 states.
    1. OK
    2. ALARM
        - Alarm is when an event has occurred and it must do the thing you set it to do.
